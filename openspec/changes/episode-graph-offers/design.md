## Context

Two use cases drive this. (1) On day one the user asks "how does tool calling work?" and gets a short answer; on day two they are doing AI work and Sutra offers a worked example. (2) Out of nowhere, a snowstorm is coming and the user planned to drive in the mountains; Sutra says so.

The user's direction: no fixed amounts, Sutra works out what is worth offering and keeps adjusting; conversations should form a graph linked by meaning; a subagent should spot a similar conversation and tell the orchestrator to make an offer; non-conversation offers can arrive at any time, roughly once a day.

Constraints inherited from the project: speaking up must stay conversational and low-stakes (the user said Sutra need not always ask first, as long as it sounds like a person, not a form), and anything that acts, spends or changes data still needs the normal confirmation; personal and financial talk must never feed this; cost stays small; the user can see and delete everything; the model can never confirm anything.

## Goals / Non-Goals

**Goals:**
- Keep conversations as a semantic graph that later conversations can be matched against.
- Let a subagent advise the orchestrator, which decides and asks.
- Replace timers with a judgement that learns from the user's reactions.
- Handle conversation-derived and outside-world offers through one arbiter.
- Keep safety rails in code, and keep everything visible and deletable.

**Non-Goals:**
- Producing outside signals (weather, calendar, research): `idle-research` and gateway tools.
- Embeddings or a vector store now.
- Quizzes, mastery tracking, spaced repetition.
- Acting on anything unprompted: offers are speech only.

## Decisions

**1. Episodes are nodes.** An episode is a coherent stretch of conversation on one subject. It closes when the subject changes or after an idle gap, then a small-model call with a forced schema writes one node: `topic` (at most 60 characters), `gist` (at most 300, what was covered), `mode` (`explained`, `planned`, `worked_on`, `decided`, `asked`), `open` (what is unfinished: `example`, `deeper`, `practice`, `decision`, or none) and `entities` (a few short nouns). The node is built from the user's own utterances plus Sutra's reply on turns that used no tool; on turns that used a tool only the user's utterance counts, and turns using excluded tools (default `finanxe_`) contribute nothing, the same rule the interests reflector uses. Alternative: one node per turn. Rejected: too fine to carry meaning, and it multiplies model calls.

**2. Edges carry a type, a strength and a reason.** After a node is written, a linker subagent sees it with a bounded candidate set (decision 3) and returns zero or more edges: `same_topic`, `extends`, `prerequisite_of`, `applies_to` (a concept used in a project), `updates` (a later fact changes an earlier one). Each edge has a strength from 0 to 1 and a one-sentence reason in words, so the user can read why two conversations are linked. Code validates ids and types; an edge to a non-candidate is dropped. A `same_topic` link with high strength merges the new episode into the older node's history instead of creating a parallel node, so repeating a question strengthens one node.

**3. Retrieval is lexical now, behind an interface.** A `Retriever` returns candidates for a piece of text: a bounded lexical match over topic, gist and entities, plus the graph neighbours (one hop) of recently touched nodes, ranked by overlap, recency and edge strength. Embeddings are not in the stack, and word overlap alone fails "tool calling" versus "building an agent", so the retriever only *proposes* candidates and the subagents judge them. If embeddings are added later they replace the retriever without touching anything else. The candidate set is capped by prompt size (a rail), not by a tuned count.

**4. The relatedness subagent advises; the orchestrator decides.** Per turn, if the retriever finds candidates and the subject has changed since the last check (a cheap code test on entities), a tools-off subagent sees the user's current utterance and their previous two utterances, plus numbered candidates with topic, gist, open items, age and past offer outcomes. It returns an advice object: `none`, or `{node, kind, benefit (0 to 1), reason, suggested_step}` where `kind` is `followup`. It is told that related means "the user's current work would plausibly benefit from this, not a shared keyword" and to return `none` when unsure. It cannot see replies, tool results or anything outside the candidates. Code validates the node id. The advice goes to the judge (decision 5); it is never shown to the user directly. Alternative: let the main model see the graph and decide while answering. Rejected: it costs tokens every turn, hides the decision inside answer generation, and cannot be tested or bounded.

**5. A judge decides whether and when, against a learned bar.** For each advice or incoming signal the judge returns `offer`, `hold` or `drop`, a `benefit` score, a `style` (`tell` or `ask`, with a short `teaser` for `ask`) and, for `hold`, its own `retry_after` (code only clamps it to a sane range so that a bad value cannot mean "never" or "every second"). The judge sees the candidate, its benefit reason, the user's recent outcomes in plain counts for this kind and this topic, how long since the last offer of any kind, and whether the user's last message looks like a short task command. Code then applies the **bar**: a per-kind number, starting neutral, that the benefit must reach. This is the learning: every outcome nudges it (accepted lowers it a little, snoozed leaves it, ignored raises it a little, declined raises it more, "stop" for a topic or kind sets a permanent block, not a bar change), and without new evidence the bar drifts back toward neutral so an old bad week does not silence the feature forever. The bar moves by small bounded steps and is clamped, so a run of declines makes Sutra quiet but never mute by accident, and a run of yeses makes it bolder but never unbounded. Alternative: a model that rewrites its own policy text. Rejected for now: harder to validate and to explain; the bar is a number the user can read and reset, and the judge's reasons are stored for the "why" command.

**6. One arbiter in front of everything proactive.** A single arbiter accepts candidates from three sources: follow-up advice, timely signals, and the interests nudge. It lets through at most one proactive item per turn, never when an action is awaiting confirmation or an offer is already open, and orders them: an urgent timely offer first, then a follow-up, then the interests nudge. The interests nudge asks the arbiter for permission through one hook; its own existing limit still applies as an additional guard, so the interest-profile change is not rewritten. The arbiter also owns the **rails**, the only fixed numbers: a daily maximum across all kinds (default 4, of which urgent timely offers may use any), a daily cap on this feature's own model calls (a count of calls, not tokens), and the explicit rule that the user's stops are final. These are guards, not the schedule: normal behaviour is decided by the judge and the bar, so on most days they never bind.

**7. Timely offers come from signals, with an expiry.** A `Signal` is `{kind, summary, source, urgency, expires_at, topic_hint}`, written to the offers store by any producer. This change provides the intake, the judging and delivery; producers are later (`idle-research`, gateway tools such as weather or calendar). For each signal the judge is shown the signal plus the graph neighbourhood retrieved for its summary and topic hint (for the snowstorm: the earlier episode where the user said they planned to drive in the mountains) and decides whether this matters to *this user now*. A signal with no connection to anything the user has said or approved is judged on general importance only, and is held to a higher bar. Expired signals are dropped without speaking; a signal that expires before a quiet moment arrives is simply lost, which is correct for a snow warning. Urgency is `low`, `medium` or `high` and comes from the producer, but is checked by code against the expiry. Weather is treated as `medium` by default. Only a `high` signal with minutes to live from a producer on a per-producer allowlist (default empty) may use the urgent path; everything else, weather included, takes the ordinary path and is judged against the bar like any other offer.

**8. Delivery is conversational and the judge picks the style.** In a voice session a timely offer is spoken at the next quiet moment through the existing notice mechanism; in text it is held for the next reply. Two styles. `tell`: one or two natural sentences stating the fact, for low-stakes, plainly useful or time-critical content ("Heads up, snow is expected on the mountain road in about twenty minutes, so you may want to hold off on that drive."). `ask`: a short teaser question whose adjective fits the content and the user's mood ("Want to hear something interesting about tool calling?", "Something good turned up for your Diwali plans, want it?"). The judge chooses; code only enforces that a `tell` never carries an action or request for data, and that an `ask` is one sentence. An alert that is safety-relevant is always a `tell`, because a teaser is useless there. After a `tell` the user may reply or ignore it with no cost; after an `ask`, yes delivers the detail. If the user is mid-reply the notice waits; if it expires first it is dropped.

**9. The follow-up offer is appended to the answer by code.** The advice and judging run beside the main model call, so they add no waiting. When the judge says `offer`, the orchestrator appends the validated teaser to the end of the finished reply, and the reply stored in history includes it so the model knows it asked. The user's own request, including tool calls, runs normally first; nothing is appended to a confirmation question, an error, or a turn that already carries a delivery. A decision that was made but not said (the turn went another way) is discarded and does not count. The interests nudge is skipped on a turn where a follow-up is being weighed or a signal is waiting. Alternative: a note in the prompt asking the model to add the question. Rejected: it makes the words depend on the model obeying, and the validated one-sentence wording is what the judge already produced.

**10. The answer to an offer is soft.** An open offer lives in a slot separate from the confirmation gate, because a confirm-first action blocks and re-asks until answered, which is wrong for a favour. At the start of the next user turn, a phrase check for "not now", "later" and "maybe tomorrow" records `deferred`; otherwise the existing classifier labels the reply against a description of the offer: affirm delivers; deny records `declined`; anything else, including a reply on another subject, records `ignored` and the turn proceeds normally with no re-asking. The slot clears after one turn whatever happens, so an offer can never capture a later unrelated "yes". Each outcome feeds the bar (decision 5) and is stored with its kind, topic and local hour.

**11. Delivery of the example is grounded.** On affirm, the turn runs the main model with a note: give one short worked example of the stated step; build it from context present in this conversation or the approved interests; if there is none, use a minimal generic example and say it is generic; plain spoken sentences, code described in words, no markdown; end with at most one question about going further. The model cannot invent facts about the user's projects. Afterwards the node's `open` item is marked done; further steps are offered only when the judge says they are worth it.

**12. Decay keeps the graph honest.** Edges and nodes fade by use: untouched, unlinked nodes lose weight over time and are eventually archived, and an archived node is not retrieved. A rail caps total stored nodes; when it binds, the weakest archived nodes are deleted first. The time constants are code defaults, not tuned per user, because the point of decay is only to keep retrieval clean.

**13. Privacy and control.** `graph.db` and `offers.db` are owner-only and separate from memory and interests. Nodes store topic, gist, entities and timestamps, never the full reply or the user's utterance. `/graph` lists episodes and shows neighbours and edge reasons; `/graph forget <id|all>` deletes. `/offers` shows recent offers with outcome and the judge's reason, the current bars, and any blocks; `/offers reset` returns the bars to neutral; `/offers block|unblock <topic|kind>`; `/offers off|on`. A local tool `stop_offers(topic?, kind?)` lets the model act on "stop offering me examples"; it can only reduce behaviour. `SUTRA_GRAPH` and `SUTRA_OFFERS` switch the parts off independently, and with the graph off, timely signals can still be judged on general importance.

**14. Voice behaviour.** A follow-up offer rides on a reply the user is already hearing. Garbled speech is not mined: turns the voice layer flags as low confidence are skipped by episode building and by advice, but text always passes. Examples are spoken in plain sentences.

## Risks / Trade-offs

- [A learned bar can drift wrong] → small bounded steps, drift back to neutral, a visible number, `/offers reset`, and permanent blocks for explicit stops.
- [The judge talks too much on day one, before any evidence] → the starting bar is moderate (0.55 for follow-ups, 0.5 for timely; a live check showed 0.7 held back the flagship case), so early on only clearly beneficial offers pass and the bar moves as the user responds.
- [Wrong relatedness] → the cost is one skippable question; nothing happens without a yes.
- [A snow warning spoken too late] → signals carry an expiry and are dropped when stale.
- [Telling without asking becomes chatter] → `tell` is for low-stakes or time-critical content, the bar and the daily rail still apply, and an ignored `tell` raises the bar like any ignored offer.
- [A timely alert becoming noisy or alarmist] → the urgent path needs an allowlisted producer, a short expiry and a connection to something the user said, and the daily rail still binds.
- [Extra cost] → model calls are event-driven and gated by the retriever and a subject-change test, with a daily call rail.
- [Personal data in the graph] → excluded tools never contribute, nodes are short concept summaries, everything can be listed and deleted.
- [Complexity] → three small packages behind interfaces (retriever, producers, judge), each testable with scripted models; the graph is a few SQLite tables, not a graph database.

## Open Questions

- Starting values for the bar and for decay constants are guesses; they need real use. They are code defaults with a reset command, not user settings.
- Weather is medium urgency by default and the urgent allowlist starts empty; which producers may ever be urgent is decided when `idle-research` and weather tools exist.
- Embeddings later: the retriever interface is the seam.
